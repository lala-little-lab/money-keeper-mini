### 入力チェック

### 立替と支払元

- 新規の「私が立替」でも、既存のポイント・割引・分割入力を記録へ反映する。実支払額は会計総額−ポイント。引落時割引は請求額へ適用し、現金等の即時残高には適用しない。集計対象の自分の分・相手の分は自動配分し直さず、入力どおり保持する。
- 楽天Payの支払元選択（楽天カード／楽天銀行／楽天Pay残高）を「私が立替」でも表示・保存する。該当する端末内口座残高へ実支払額を反映する。

- 楽天Pay残高不足は登録・編集を拒否する。編集では変更前の支払いを戻した場合に使える残高を計算して判定し、判定のために実際の残高は変更しない。

### パスワード入力の頻度と操作

- 更新後、最初の1回はこれまでのパスワードで解除。パスワード変更・再設定は行わない。新規利用時のみ12文字以上で初回設定。

### 保存方式と保護への影響

- miniSchemaVersion:4、暗号化バックアップversion:1、PBKDF2/SHA-256/310000回・AES-GCM、DB名・保存済みデータの形式は07と同じ。migrations.jsは07と同一。
- IndexedDBの同じapp_stateストアに、家計データprimaryとは別のunlock-24h項目を追加。格納内容は非抽出CryptoKey・salt・解除時刻・期限・失効確認用値。パスワード自体は保存しない。
- localStorageには失効確認用のランダムな値だけを保存し、パスワードや家計データ、鍵の文字列表現は入れない。解除保持項目は暗号化バックアップに含めず、バックアップ復元には従来どおり作成時のパスワードが必要。
- 暗号化データを残す一方、24時間以内はこのブラウザを操作できる人がアプリを開ける。非抽出CryptoKeyはWeb APIでの鍵の書き出しを禁止する指定であり、同一オリジンの不正スクリプトや端末侵害を防ぐ保証ではない。GitHub Pagesの同じオリジン内ではパスが違うだけで保存領域のセキュリティ境界になるわけではない。

- 参考仕様：W3C Web Cryptography API「Key Storage」「Security considerations」https://www.w3.org/TR/WebCryptoAPI/ 。CryptoKeyをIndexedDBで保持できる仕様を確認し、miniの実装は別途ブラウザテストした。
